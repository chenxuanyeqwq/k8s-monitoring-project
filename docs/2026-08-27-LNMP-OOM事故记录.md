# LNMP OOM 事故记录（2026-08-27）

> 状态：**已修复 ✅** ｜ 影响：https://www.fchen.xyz 全站 500 约 1 小时 ｜ 根因：内存耗尽 OOM 杀 MySQL

## 一、现象

- 网站报错：`数据库连接失败：SQLSTATE[HY000] [2002] php_network_getaddresses: getaddrinfo for db failed: Try again`
- HTTPS 返回 **500**，耗时 ~12s
- SSH 连接：`Connection timed out during banner exchange`（TCP 通、SSH 握手卡死）
- ping 正常（0 丢包）、8080 返回 301（nginx 存活）

## 二、根因链

```
2G 内存 + 12 容器超载（Loki 压垮最后一根稻草 + CI/CD 在服务器上 docker build 的内存峰值）
→ 内存耗尽 → Linux OOM killer 杀掉 MySQL 容器进程
→ PHP 解析 compose 服务名 db 失败（Docker 内置 DNS 返回 EAI_AGAIN「Try again」）
→ 数据库连接失败 → 网站 500
→ 系统持续 swap thrashing → sshd 无资源响应 → SSH banner 超时
```

## 三、定位证据（外部探测即可定位，无需进服务器）

| 探测 | 结果 | 结论 |
|------|------|------|
| ping | 33ms，0 丢包 | 服务器活着，**网络正常** |
| 8080 直连 | HTTP 301，0.05s | nginx 存活（301 是 nginx 自己发，不经过后端） |
| HTTPS | HTTP 500，~12s | **PHP/MySQL 后端挂了** |
| SSH banner | 握手超时 | **系统 swap thrashing，sshd 抢不到 CPU** |

> 关键判断：SSH「banner 超时」≠ 服务器死（ping 通），而是**内存耗尽、系统在 swap 里挣扎**——这是内存问题的典型信号。

## 四、恢复动作

1. SSH 已卡死进不去 → **阿里云控制台「重启实例」**（数据在 volume 里，重启安全）
2. 重启后 LNMP 三容器为 `Exited (255)`——**compose 未设 restart 策略，重启不自启**
3. `cd /opt/k8s-project/01-lnmp && docker compose up -d` 手动拉起 → 网站恢复 200
4. 监控栈（cm-*）因自带 `restart: unless-stopped`，重启后自动恢复

## 五、修复（护栏，已落地并验证）

### 1. LNMP 栈 `01-lnmp/docker-compose.yml`
- 三服务加 `restart: unless-stopped` → **服务器重启自动拉起**（根治「重启不自启」）
- 加 `mem_limit` 内存护栏：nginx 128m / php 256m / mysql 768m
- MySQL 显式 `--innodb-buffer-pool-size=128M`（实测 MySQL 占 ~384M，锁死上限）

### 2. 监控栈 `07-cloud-monitoring/docker-compose.monitoring.yml`
- 9 个容器加 `mem_limit`：grafana / prometheus / loki 各 256m，promtail 128m，其余 64~128m

### 3. 护栏设计原理
**全部容器 mem_limit 上限之和 < 物理内存 + swap（2G+2G=4G）** → 即使所有容器同时撞上限，也轮不到 OOM killer 出手。

### 验证结果
- 12 容器全 running，总占用 ~734MiB，可用内存 ~600MiB
- 网站 HTTPS 200（0.04s，恢复前是 12s）

## 六、教训与复盘

1. **2G 内存带不动 LNMP + 全监控栈 + Loki**——容量规划是硬约束，护栏只是兜底，不是根治
2. **compose 必须设 restart 策略**，否则服务器一重启服务就静默消失
3. **内存峰值主凶：在服务器上 `docker build`**（CI/CD deploy.sh）——构建应挪到 CI + 镜像仓库，服务器只拉镜像
4. **面试话术**：一条完整断线根因链「内存耗尽→OOM→MySQL 被杀→DNS EAI_AGAIN→500」+ 外部探测三步定位（ping/8080/HTTPS）+ SSH banner 超时 = thrashing 信号
