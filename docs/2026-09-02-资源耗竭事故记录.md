# 服务器资源耗竭级联崩溃事故记录（2026-09-02）

> 状态：**已修复 ✅** ｜ 影响：https://www.fchen.xyz 全站不可用约 1.5 小时 ｜ 根因：1.6Gi 内存跑 LNMP + 12 容器监控栈长期余量不足 + snapd 死循环吃 CPU → swap thrash → 守护进程级联死亡（**非经典 OOM**）

## 一、现象

- 网站报错：`数据库连接失败：SQLSTATE[HY000] [2002] php_network_getaddresses: getaddrinfo for db failed: Try again`（与 8/27 相同）
- HTTPS 完全无响应（TCP 通、HTTP 挂起）；SSH `Connection timed out during banner exchange`
- **云助手 Agent 未运行**——sshd 之外的第二个通道也死了，确认系统级僵死
- ping 正常（31ms 0 丢包）、8080 秒回 301（nginx 存活）

## 二、根因链

```
1.6Gi 可用内存跑 LNMP + 12 容器监控栈(Loki/Grafana/Prometheus/fail2ban)
→ 可用内存长期仅 ~300-475MiB（基线就是薄的）
+ snapd.service 死循环重启 523 次（start timed out，持续消耗 CPU）
→ 内存压力 → swap thrash → 守护进程逐个被饿死（级联）：
   09-01 07:00  监控栈先死（Prometheus 记录中断）
   09-01 12:29+ mysqld-exporter 全天间歇连不上 MySQL
   → MySQL 被 SIGKILL → PHP 解析 db 失败 EAI_AGAIN → 网站挂
   → 09-02 上午 sshd / 云助手 / Docker 全僵死 → 控制台重启也卡住（OS 不响应 ACPI）
```

**关键区别（vs 8/27）**：8/27 是**单点 OOM killer 杀 MySQL**（有 oom-kill 记录）；这次**无 OOM-kill 记录**，是慢性耗竭下的级联死亡——journald 显示 snapd 死循环 + 各守护进程陆续消失，像"慢慢饿死"而非"一刀砍死"。**mem_limit 护栏能防单容器 OOM，防不住宿主级 swap thrash**。

## 三、定位证据

### 外部探测（无需进服务器即可判断）

| 探测 | 结果 | 结论 |
|------|------|------|
| ping | 31ms 0 丢包 | 服务器活着，网络正常 |
| 8080 | HTTP 301 秒回 | nginx 存活（纯重定向不碰后端） |
| 443 | 无响应 | PHP/MySQL 栈死 |
| SSH banner | 握手超时 | 系统 thrashing，sshd 抢不到 CPU |
| 云助手 | Agent 未运行 | 第二通道也死 → 系统级僵死 |

### 进服务器后证据（Prometheus tsdb 幸存是破案关键）

- **Prometheus 数据卷幸存** → 09-01 07:00 后监控记录中断，此前可用内存稳定在 316-420MiB
- **mysqld-exporter 容器日志**：09-01 全天多次 `context deadline exceeded` / `i/o timeout`
- **lnmp-mysql 容器日志**：8/27 → 9/2 直接跳转，无正常关停 = **被 SIGKILL**
- **journald 持久日志**：`snapd.service` restart counter **523**，`start operation timed out` 循环
- **磁盘仅 25%、inodes 6%** → 排除磁盘写满

## 四、恢复动作

1. SSH / 云助手全不可用 → 阿里云控制台「重启实例」→ **卡在「停止中」**（OS 不响应 ACPI 关机信号）
2. 强制停止遇 `InvalidOperation.Conflict`（卡住的重启任务占着实例操作锁）→ **等任务超时释放锁**
3. 状态回「运行中」但系统未真正重启（8080 仍秒回）→ 立即「**强制停止**」→ 已停止 →「启动」
4. 重启后 12 容器全自动拉起（8/27 已加 `restart: unless-stopped`），lnmp-mysql healthy，网站恢复 200

## 五、修复（加固，已落地并验证）

### 1. 停用 snapd（低配机无用还死循环吃 CPU）
- `systemctl disable --now snapd snapd.socket`（可逆：`enable --now` 即恢复）
- 死循环原因：低内存下 snapd 启动超时 → systemd 反复拉起 → 白吃 CPU

### 2. 新增 LowMemory 内存预警（补告警盲区）
- 之前告警规则只有 HighCPUUsage / HighDiskUsage / High5xxRate / MySQLDown，**没有内存告警** → 这次监控自己先死都没人知道
- 新增规则：`node_memory_MemAvailable_bytes < 300MiB` 持续 10min → 飞书 warning（崩溃前约 10-15 分钟预警，比黑盒探测早）
- 已落地 `07-cloud-monitoring/prometheus/rules.yml` + `docker kill -s HUP cm-prometheus` 热重载，5 条规则全加载、当前 inactive

### 3. 验证结果
- 12 容器全 running、lnmp-mysql healthy、网站 HTTPS 200
- 内存基线 ~400-475MiB 可用（仍然薄，需结构性解决）

## 六、教训与复盘

1. **容量规划是硬约束**：1.6Gi 跑 LNMP + 全监控栈余量只有 ~400MiB，这是第三次濒临资源问题。mem_limit 只能防单容器 OOM，**防不住宿主级 swap thrash**
2. **监控自身的存活要先于监控对象**：Prometheus 09-01 07:00 就死了，导致崩溃全程无监控数据。LowMemory 告警就是要赶在监控死之前报警
3. **多通道保障**：SSH 和云助手双通道都依赖系统进程，系统级僵死时只剩「强制停止 + 重启」一条路。控制台重启卡「停止中」时用「强制停止」即可
4. **持久化监控数据 = 事后定位的破案关键**：Prometheus 数据卷 + 容器日志 + journald 交叉验证，能还原完整崩溃时间线
5. **面试话术**：8/27 OOM vs 9/2 非 OOM 级联的对比判断、mem_limit 的边界、告警盲区（无内存预警）、恢复路径（重启卡住 → 强制停止）——比单讲一次 OOM 更有深度
