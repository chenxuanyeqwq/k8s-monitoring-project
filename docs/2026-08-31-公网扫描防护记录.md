# 公网扫描防护记录（2026-08-31）

> 状态：**已防护 ✅** ｜ 影响：https://www.fchen.xyz 被自动化扫描器刷量 25 分钟 ｜ 根因：公网 IP 被凭据泄露/SSRF 扫描器盯上 + nginx 放大未知路径为 MySQL 查询

## 一、现象

- Grafana 面板：**nginx 请求率 + MySQL 查询率同步飙升**
- 单 IP `34.80.5.60`（GCP 台北 VM）6 小时内 8726 次请求，其中 8860 条集中在最近 1 小时（16:25 北京时起 25 分钟打 8000+）
- 路径全是凭据泄露/SSRF 探测：`/.env`、`/.git/config`、`/.aws/credentials`、`/.azure/credentials`、`/actuator`、`/webhook?url=169.254.169.254/latest/meta-data/...`（云元数据 SSRF）、wp-config*、`*.swp/*.old/*.bak`
- UA 全伪装：Perplexity-User / ChatGPT-User / Claude-User / GrokBot / Applebot / Slackbot 轮换，同 IP 每秒换一个身份

## 二、根因链

```
公网 IP 暴露(www.fchen.xyz 无需备案直连)
→ 被凭据泄露扫描器盯上（租 GCP VM，伪造爬虫 UA 探测 .env/.git/云元数据）
→ 命中即放大：nginx location / { try_files $uri $uri/ /index.php } 让任意未知路径都落 index.php
→ 每个探测请求 → PHP 渲染首页 → MySQL 查留言列表（放大成一次数据库查询）
→ 8726 次探测 = 8726 次 MySQL 查询 → nginx 请求率 + MySQL 查询率同步飙升
```

> 关键判断：扫描器是"凭据泄露探测"（找 `.env`/AWS 凭据/云元数据），不是 DDoS——目的是偷数据不是打死服务，但**放大器的存在让它每请求都烧数据库**。

## 四、防护动作（纵深防御 4 层）

### ① 手动封禁当前 IP（DOCKER-USER 链）
```bash
iptables -I DOCKER-USER -s 34.80.5.60/32 -j DROP
```
⚠️ **关键坑**：Docker 端口流量走 FORWARD→DOCKER-USER 链、**不过 INPUT 链**（`-P FORWARD DROP`）。封 INPUT 不生效，必须封 `DOCKER-USER`。

### ② nginx 关放大器
`location /` 的 `try_files $uri $uri/ /index.php?$query_string;` → `try_files $uri $uri/ =404;`
- 未知路径不再落 index.php，扫描器刷 N 次只产生 N 个空 404，不再放大成 PHP+MySQL
- 安全性前提：留言板**无 clean URL**（index.php 只处理 `/` 与 `/index.php`），改 404 不破坏功能

### ③ nginx 敏感路径屏蔽（`return 444` 断连）
```
/.env .git .aws .ssh .svn .hg .DS_Store .htaccess ... → 444
wp-config* wp-login xmlrpc phpmyadmin adminer actuator composer/package json ... → 444
*.sql *.bak *.old *.swp *.tmp *.tar.gz *.zip ... → 444
vim 备份 foo~ ... → 444
169.254.169.254 metadata.google /latest/meta-data (SSRF, 用 $request_uri 匹配查询串) → 444
```
黑名单正则 location 必须放在 `location ~ \.php$` **之前**（正则 location 按文件顺序匹配）。

### ④ fail2ban 自动封禁
- filter `nginx-probe`：按**请求路径特征**匹配（与状态码 301/404/444 无关，301 的探测也能捕获）
- jail：findtime 60s / maxretry 6 / bantime 1h，`ignoreip` 含本机 + 自己公网 IP（黑盒探测源）
- action：`iptables-multiport[chain=DOCKER-USER]`（同①的坑，必须 DOCKER-USER）
- 日志源：nginx bind mount 真实 `access.log`（**stdout 双写保住 Loki**）——直接读 docker json-log 的话容器重建后路径含容器 ID 会失效
- systemd 内存护栏 `MemoryMax=128M`（实测 RSS 15MB）+ logrotate copytruncate

## 五、验证结果

- 加固后：`/.env`→444、`/.git/config`→444、`/actuator`→444、`/random/nonexistent`→**404**（不再是 200！）、`/`→200、POST→302、HTTP→HTTPS 301 全对
- Loki 仍收到 nginx 日志（stdout 双写生效，promtail 不受影响）
- fail2ban-regex 离线自检 4/4 命中（修了一个正则坑：`\S*` 贪婪吞掉探测特征 → 改 `\S*?` 惰性匹配）
- fail2ban banip 实测：DOCKER-USER 出现 f2b-nginx-probe 链 + DROP，正常访问 200 不受影响
- CI/CD 部署后服务器配置不被覆盖（nginx.conf/日志卷仍在）——**三端同步**（服务器/本地/GitHub）

## 六、教训与复盘

1. **Docker 端口流量不过 INPUT 链**——封禁/限流挂 FORWARD/DOCKER-USER，这是容器防火墙最容易踩的坑
2. **"未知路径全落 index.php"是放大器**——扫描器每请求都放大成数据库查询，先关放大器再谈封禁
3. **公网服务一定会被扫**——凭据泄露扫描器反复来、IP 会变，手动封禁是止血、fail2ban 自动封禁才是兜底
4. **fail2ban 读 docker 日志要处理容器 ID 变动**——bind mount 真实文件最稳
5. **面试话术**：一条扫描识别链「请求率+查询率同步飙升 → 按 IP 聚合定位单源 → 路径特征识别凭据泄露扫描 → 放大器解释指标联动 → DOCKER-USER 封禁 + fail2ban 兜底」
